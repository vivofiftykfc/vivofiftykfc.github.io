An Introduction to Git and Its Use

This post consists of notes taken while reading the official Pro Git Book. Much of it was copied directly. I read only the first two chapters for this post; subjects such as running Git on a server can wait until later.

A Brief History of Git

The Development of Version Control

Local version control → centralised version control → distributed version control.

Git emerged during the development of Linux. After BitKeeper, a distributed version-control system, withdrew the Linux development team’s right to use it free of charge, Linus Torvalds led the creation of a new version-control system. Git was designed to be simple and fast, to support parallel development, to be fully distributed, and to manage projects on an extremely large scale.

Underlying Idea and Advantages

Git records an index of file snapshots. Whenever an update is committed, it takes a snapshot and stores an index pointing to that snapshot. For efficiency, if a file has not changed, Git does not store it again but retains a link to the previously stored file. Most Git operations therefore need access only to local files and resources and generally require no information from other computers on a network.

Earlier systems such as CVS, Subversion, and Perforce instead recorded differences between successive versions in a form resembling patches, an approach usually called delta-based version control. With Perforce, almost nothing can be done without a connection to the server. With Subversion and CVS, files can be modified offline, but the changes cannot be committed to the database because the local machine has no complete offline database.

Git recognises three principal states in which a file may exist: committed, modified, and staged.

  • Modified means that the file has changed but has not yet been stored in the database.
  • Staged means that the current version of a modified file has been marked for inclusion in the next committed snapshot.
  • Committed means that the data has been safely stored in the local database.

A Git project consequently involves three areas: the working tree, which is an independent copy of one version that can be edited; the staging area, a file in the Git repository directory that records what the next commit will contain; and the Git directory, .git.

Installing Git

  • Linux, using a Debian-based distribution as an example: sudo apt install git-all
  • macOS: run git --version and follow the system prompts. For direct installation with a binary installer, see the Git website: Git—Downloading
  • Windows: use the binary installer described at Git—Downloading Package
  • Compilation from source: see Git—Installing Git. I do not think this is necessary, and it consumes additional time, though anyone interested may try it.

Configuring Git

Git provides the git config tool. Configuration variables may be stored in three locations:

  1. For every user on the system: /etc/gitconfig. If git config is run with the --system option, Git reads from and writes to this file. Note that it is a system configuration file and requires sudo privileges.

  2. For the current user: ~/.gitconfig or ~/.config/git/config. Passing the --global option causes Git to read from and write to this file, affecting every repository belonging to the user.

  3. For the current repository: .git/config. Within that repository, the --local option forces Git to read and write this file, although this is already the default behaviour.

A setting at each more specific level overrides the corresponding setting at the broader level above it.

On Windows, Git looks for a .gitconfig file under the &#36;HOME directory, generally C:\Users\&#36;USER. It also looks for /etc/gitconfig, but only under the root directory of MSys—that is, the destination selected when Git was installed. If Git 2.x or later is used on Windows, another system-level configuration file exists: C:\Documents and Settings\All Users\Application Data\Git\config on Windows XP, or C:\ProgramData\Git\config on Windows Vista and later. This file can be modified only with administrator privileges by running git config -f <file>.

Tracking New Files and Staging Changes

A file cannot be placed under version control until it has been added to the update. A newly created file remains untracked, and git add <文件> must be run to stage it. Every subsequent commit includes only the contents of the staging area. git add can also accept a directory path and recursively track every file beneath it.

One detail deserves attention. If a new file is added halfway through the work, the version eventually uploaded is the version that existed when git add was last run. Any modifications made afterwards remain unstaged, so the file must be added again.

Ignoring Files That Do Not Need Version Control

Create a .gitignore file in the project root, or in a subdirectory, and list the patterns to be ignored. Glob syntax is supported.

Inspecting File Status

  • git status displays the current branch, its relationship with the remote branch, staged and unstaged changes, and untracked files.
  • git status -s, or --short, displays the same status in a compact form.

Inspecting the Details of Changes

Before committing, use git status to confirm that every required change has been staged, and then inspect the differences.

One distinction is important. To view only unstaged changes, run git diff. To inspect changes that are staged and waiting to be committed, use git diff --cached, or --staged.

Removing Files

1. Complete Removal from Both the Working Directory and Git Repository

git rm <file>:

  • Deletes the file from the working directory.
  • Stages the deletion by recording it in the staging area.
  • After the commit, the file is no longer tracked by Git and has disappeared from the disk.

2. Removal from Git Tracking Only, while Retaining the Working-Tree File

git rm --cached <file>:

  • Removes the file from Git’s tracking list and staging area.
  • Retains the file in the working directory, where it becomes untracked.
  • This is useful when a file was added accidentally but must remain locally, as with a log or build artefact.

3. Forced Removal with -f

  • If a file has been modified and staged, git rm -f <file> is required to force its deletion.
  • This requirement helps prevent accidental deletion of modifications for which no committed snapshot exists and which Git therefore cannot restore.

4. Removing Files That Match a Pattern

  • Use git rm with a glob pattern; for example, git rm log/\*.log deletes every .log file under log/.
  • Note: special characters such as * generally need to be escaped, as in \*.

Committing Changes

Running git commit opens the default text editor with a comment template for the commit, resembling the commented lines shown by git status. Enter the commit message on the first line. Alternatively, git commit -m "提交信息" places the message directly on the command line. Each git commit should implement one feature or fix one bug. The message must be clear—must be, must be.

After the commit, Git reports the current branch, the SHA-1 generated for the commit, and statistics such as the number of files and lines involved.

Each commit records only a snapshot of the staging area. Unstaged changes are not included and remain in the working directory; git add must be run again before they can enter a later commit.
